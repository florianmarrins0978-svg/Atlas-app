Ce que le code devra faire (niveau 3 : c'est de l'argent)

↑ Sommaire
  1. La règle (src/lib/abonnements.ts) : une liste fermée de modules, son prix, ses fonctions ; fonctionOuverte lit la formule ET les modules ; la ligne des salariés devient réservée ; Artisan compte tous les accès, pas seulement ceux qui facturent.
  2. La base : les modules souscrits, sur la ligne d'abonnement, en expand (colonne ajoutée, vide par défaut).
  3. Le paiement : une seconde ligne dans la page de paiement, et l'ajout ou le retrait du module au prorata sur un abonnement qui court ; les modules relus au retour et au crochet, comme la formule.
  4. Les deux refus : inviter un salarié sur Artisan, et passer à Artisan avec d'autres comptes.
  5. Les écrans fermés : « Le plan d'arrosage est dans Entreprise » devra proposer aussi le module.
  6. La facture d'abonnement de Cause : deux lignes au lieu d'une.

Ce qui a été trouvé en chemin

↑ Sommaire
  • Un écart déjà là, sans rapport avec le module : passer d'Entreprise à Artisan avec trois personnes qui facturent n'est refusé nulle part aujourd'hui (le plafond ne se vérifie qu'à l'invitation), alors que l'article 14.6 le promet. Le refus du point 4 le fermera.
  • Les conditions générales publiées (version 3) disent le contraire : « Les comptes salarié ne sont pas comptés et ne donnent lieu à aucun supplément, quel que soit leur nombre », et le module n'y existe pas. Il faudra une version 4, que chaque compte acceptera de nouveau. La publier est sa décision.
  • PRODUCT.md dit encore que l'arrosage, le diagnostic et les fiches « font partie du cœur, pas d'un module optionnel ». À corriger au codage.
